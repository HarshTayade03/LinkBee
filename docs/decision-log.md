# Architectural Decision Log (ADR)

This file tracks all significant architectural, technical, and security decisions made during the project lifecycle.

| ID | Phase | Decision | Alternatives Considered | Why We Chose This | Trade-off / Drawback |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **ADR-001** | Phase 0 | Clean separation of API service (`/api/v1`) from Redirection handler (`/:code`) | Single monolithic route handler | Separates hot redirection read path from colder management CRUD; allows independent caching, middleware, and rate limits. | Slight duplication of routing definitions; requires explicit route precedence in Express to avoid colliding with reserved prefixes. |
| **ADR-002** | Phase 0 | Ephemeral management token model (hashed with SHA-256) instead of full Auth/User system | Full JWT/OAuth2 user session & account system | Keeps scope focused on backend engineering and systems fundamentals without boilerplate user registration/login tables. | Users cannot recover access to manage links if they lose their one-time management token. |
| **ADR-003** | Phase 0 | PostgreSQL over MongoDB or SQLite | MongoDB (NoSQL document store), SQLite | Relational integrity, ACID compliance, native indexes, and support for high-throughput transactional writes with explicit schemas. | Slightly higher initial setup cost and resource overhead than SQLite. |
| **ADR-004** | Phase 0 | Redis for Cache-Aside and Atomic Fixed-Window Rate Limiting | Memcached, in-memory Node process cache | Native atomicity (`INCR`), key expiration (`EXPIRE`), and decoupled shared state across multiple Node instances. | Added infrastructure dependency; application must handle fallback if Redis is unavailable. |
| **ADR-005** | Phase 0 | 302 Found (Temporary Redirect) over 301 Moved Permanently | 301 Moved Permanently | Browsers aggressively cache 301 redirects locally, bypassing the backend on subsequent clicks, which prevents accurate real-time click analytics. | Marginal latency overhead on repeat visits since clients must re-query server instead of using local browser cache. |
| **ADR-006** | Phase 1 | Cryptographic Random Base62 (7 chars) over Sequential Auto-Increment + Base62 | Sequential ID (`id=1 -> '1'`, `id=2 -> '2'`) encoded with Base62 | Sequential IDs leak internal business velocity, total volume, and are easily scraped via enumeration attacks. High-entropy random Base62 provides ~3.52 trillion combinations without revealing creation sequence. | Rare chance of collision requiring application-level retry on `unique_violation` (23505) in PostgreSQL. |
| **ADR-007** | Phase 1 | Host Port Mapping 5433:5432 in Docker Compose | Default 5432:5432 | Developer machines frequently run an existing local PostgreSQL service on default port 5432. Mapping host port 5433 prevents port collision while keeping the internal container port standard (5432). | Developers must use port 5433 when connecting from host tools. |
| **ADR-008** | Phase 2 | Strict URL Protocol Whitelisting (`http:` and `https:`) | Allowing any protocol or regex URL matching | Prevents severe protocol injection attacks (e.g. `javascript:alert(1)` for XSS, `data:` URI payloads, `file:///etc/passwd` local file access). | Disallows niche schemes (like `mailto:` or `ftp:`), which are inappropriate for a web URL shortener anyway. |
| **ADR-009** | Phase 2 | HTTP 409 Conflict for Alias Collision vs Internal Retry for Random Code Collision | Retrying custom aliases automatically or treating both as generic 500 errors | When a user explicitly requests a custom alias that already exists, it is a client conflict (`409 Conflict`), requiring the user to pick another name. When a random code collides, it is a system artifact that the server must resolve silently via retries. | Requires distinguishing between user-supplied aliases and auto-generated short codes in service logic. |
| **ADR-010** | Phase 2 | HTTP 410 Gone vs HTTP 404 Not Found for Expired Links | Returning 404 for both non-existent and expired links | RFC 9110 specifies `410 Gone` indicates the target resource once existed but is intentionally no longer available, allowing clients, scrapers, and caches to permanently purge references. | Requires querying the record first and checking timestamps rather than treating expired records as nonexistent at the DB filter level. |
| **ADR-011** | Phase 3 | Cache-Aside (Lazy Loading) with Fail-Open Degradation | Write-Through caching or Fail-Closed error throwing | Cache-aside ensures only actively requested links occupy expensive RAM cache. Fail-open ensures that if Redis goes down, requests transparently fall back to PostgreSQL without breaking redirect traffic for users. | Cold requests experience a cache-miss penalty on their first hit; cache stampede must be accounted for on viral links. |
| **ADR-012** | Phase 3 | Redis Eviction Policy: `allkeys-lru` with 256MB cap | `noeviction` or `volatile-lru` | Prevents Out-Of-Memory (OOM) crashes by automatically evicting Least Recently Used (LRU) keys when RAM fills up. | Very old, dormant links will be evicted to make room for viral links, which is acceptable since PostgreSQL remains the persistent source of truth. |
| **ADR-013** | Phase 4 | Asynchronous Fire-and-Forget Click Logging (`setImmediate`) | Synchronous blocking insert or external message queues (Kafka/RabbitMQ) | Ensures click tracking never delays the user's redirect latency; keeps architecture lightweight without requiring heavy distributed message broker dependencies. | Under sudden process crashes, a small fraction of in-flight click events could theoretically be lost before reaching PostgreSQL. |
| **ADR-014** | Phase 4 | Composite Index on `clicks(url_id, clicked_at DESC)` | Single-column indexes on `url_id` and `clicked_at` | Enables PostgreSQL to satisfy queries for a specific URL's recent clicks using an Index-Only Scan without reading full heap tables or sorting in memory. | Slight write amplification during click inserts. |
| **ADR-015** | Phase 4 | Zero Raw IP Address Storage (Privacy-Preserving Analytics) | Storing full client IPv4/IPv6 addresses in `clicks` table | Avoids storing Personally Identifiable Information (PII) under GDPR and CCPA, reduces compliance liability, and minimizes table row size. | Cannot perform fine-grained unique visitor IP de-duplication without hashing or hyperloglog. |
